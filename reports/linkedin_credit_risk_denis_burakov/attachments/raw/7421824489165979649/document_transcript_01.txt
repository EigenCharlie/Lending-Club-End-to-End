Overview This chapter demonstrates how to deploy MLflow Tracking Server infrastructure for Amazon SageMaker Studio using AWS SAM (Serverless Application Model). MLflow provides experi- ment tracking, model versioning, and artifact storage capabilities essential for production ML workflows. The architecture uses AWS SAM to deploy IAM roles and policies, enabling MLflow integration with SageMaker Studio for centralized experiment management. MLflow was first integrated with Amazon SageMaker in June 2024 and is now the recommended replacement for SageMaker Experiments. In 2025, AWS announced MLflow Apps as the default tracking experience for SageMaker Studio, providing a serverless tracking experience. Since MLflow Apps are difficult to replicate locally, this chapter focuses on the classic MLflow Tracking Server deployment pattern that works nearly identically in local development and production. For local development, we use Docker Compose to run LocalStack (for CloudFormation and IAM), PostgreSQL (for MLflow metadata), and MLflow Tracking Server (for experiment tracking). SageMaker Local Mode enables training models in Docker containers that log metrics and artifacts to the local MLflow server, providing a complete development environment without AWS costs. Key Learning Objectives By the end of this guide, you will understand: • How to deploy MLflow infrastructure using AWS SAM templates • IAM role configuration for MLflow Tracking Server and SageMaker integration • Training models with SageMaker Local Mode and MLflow experiment tracking • Artifact storage in S3 with PostgreSQL backend for metadata • Local development workflow using LocalStack and Docker Compose Why MLflow? MLflow is an open-source platform for managing the ML lifecycle, including experimentation, reproducibility, and deployment. It provides four main components: • MLflow Tracking: Record and query experiments (parameters, metrics, artifacts) • MLflow Projects: Package ML code in a reusable, reproducible format • MLflow Models: Deploy models in diverse serving environments • Model Registry: Store, annotate, and manage models in a central repository 1

MLflow in SageMaker Studio Amazon SageMaker has progressively integrated MLflow as the primary experiment track- ing solution: • June 2024: MLflow Tracking Server support added to SageMaker Studio • 2025: MLflow Apps announced as the default tracking experience • S3 Backend: SageMaker MLflow uses S3 for artifact storage (not filesystem) • Serverless: MLflow Apps provide managed, serverless tracking (likely ECS-based) This chapter focuses on the classic deployment pattern using SAM, which provides more control and works consistently across local and production environments. Architecture Components The MLflow infrastructure consists of AWS SAM-deployed IAM resources and a local Docker Compose stack for development. The SAM template creates IAM roles and policies required for SageMaker Studio to use MLflow Tracking Server. AWS SAM Template The SAM template (template.yaml) deploys the following resources: SAM-Deployed Resources 1. MLflowTrackingServerRole: IAM role for MLflow Tracking Server • Trust policy allows sagemaker.amazonaws.com to assume the role • Includes AmazonSageMakerFullAccess managed policy • Custom policy for S3 artifact access and CloudWatch logging 2. SageMakerMLflowPolicy: IAM policy attached to existing SageMaker execution role • MLflow Tracking Server management permissions (Create, Update, Delete, Start, Stop) • SageMaker Studio permissions for session management • IAM PassRole permission for MLflow role • S3 and CloudWatch Logs permissions Local Development Stack The Docker Compose configuration (docker-compose.yml) provides a complete local devel- opment environment: 2

Model Logging APIs MLflow API Considerations MLflow provides two approaches for storing model artifacts: • log_artifact(): Stores any file (plots, binaries, config). Simple and reliable, works with- out REST API configuration. • log_model(): Flavor-specific model logging (sklearn, CatBoost, PyTorch). Requires MLflow 3.0+ with logged-models API support. More convenient for deployment work- flows. This implementation uses mlflow.sklearn.log_model()with MLflow 3.0+ which supports the logged-models API for better model tracking and deployment integration.
