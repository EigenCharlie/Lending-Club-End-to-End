    A client came to us to “simplify” their ML platform using SageMaker Feature Store, which was burning ~$7–8K/month. Here’s what we saw 👇 The client was already using SageMaker for training and inference. Reasonable choice. They added Feature Store to centralize features and reduce engineering overhead. On paper: • Clean architecture • Fewer custom components In practice: 💸 High recurring costs for a simple workload. What the usage actually looked like • ~50M online feature reads / month • ~100GB stored • Online + offline store enabled Feature Store pricing included: • Online read/write requests • Data ingestion • Offline store (S3 + Glue) • Metadata and versioning overhead 📊 Total cost: ~$7–8K/month But here’s the key insight: They weren’t using: • Historical feature backfills • Offline/online consistency guarantees • Feature versioning or schema enforcement They only needed low-latency feature lookups at inference time. Our recommendation We suggested replacing Feature Store’s online usage with DynamoDB. Same latency. Fewer moving parts. Much lower cost. DynamoDB (steady traffic): • Reads (10 RCUs): ~$95/month • Writes (5 WCUs): ~$60/month • Storage (100GB): ~$25/month 💰 Total: ~$180/month (< $400/month even with traffic spikes) The takeaway SageMaker Feature Store’s online store is built on top of DynamoDB. It’s a powerful service, but you pay for guarantees and abstractions that not every workload needs. Our role wasn’t to add more AWS services. It was to ask: “What does the client actually need?” If you’re running ML workloads on AWS and your Feature Store bill looks suspiciously high, it might be time for a second look. #aws #mlops #costoptimization #cloudarchitecture #sagemaker #dynamodb

When you write code yourself, comprehension comes with creation. When machines write it, you must understand during review. Software may move to production before validation. Combined with AI hallucinations, this creates serious risk. Code reviews become more critical in an AI world, not less. They're the control point for human judgment. Kiro IDE: Spec-Driven Development The core problem with AI coding assistants is ambiguity. Vibe coding generates code immediately, leaving you to iterate. Spec-driven development introduces an intermediate step. Instead of jumping to code, Kiro IDE generates requirements, designs, and tasks. You iterate on specifications until they match your mental model, then generate code. This shifts iteration from code-level to intent-level.     There are many ways to setup your AI/ML model for inferencing. One approach of AWS is using SageMaker endpoints. They can work well but they run 24/7, even when nobody is using them. For side projects or sporadic workloads, that baseline cost adds up quickly—$36-171/month before you make a single prediction. One alternative is to use AWS Lambda for inferencing. You can export many models to ONNX format and run inference on serverless compute. You pay per request instead of per hour. At 100k monthly requests with the example setup below it is roughly $0.35 vs $36. The break-even point is somewhere around 10 million requests. Cristopher Coronado shows how to set this up including math on hidden costs like S3 storage and cold starts. The project is open source if you want to try it yourself. https://lnkd.in/efN7jj_P
